# macOS 제품 프로그램 구조

## 상태와 맥락

Accepted. 사용자가 Swift·AppKit + CEF 채택과 추가 검증 종료를 명시하고 프로그램 구조 작성을 요청했다. 기존 기술 설계의 채택 보류 문구를 현재 결정과 구분했다. 미완료 검증을 통과로 바꾸지 않는다.

## 전제

단일 사용자 로컬 macOS 앱, 검색·이미지 탐색 중심, 소규모 초기 제품이다. 현재 Windows 코드 공유를 고려하지 않는다. 앱 UI·프로필과 로컬 저장이 필요하므로 서버용 무상태·외부 DB 원칙은 적용하지 않는다.

## 선택과 대안

기존 기능별 Swift 폴더를 유지하고 app, workspace, browser, platform/macos, storage 경계를 구체화했다. 기능마다 독립 프레임워크를 만드는 방안은 초기 연결 비용이 커서 선택하지 않았다. 단일 거대 AppDelegate에 CEF·저장·정책을 모두 넣는 방안은 소유권과 엔진 결합이 불명확해 선택하지 않았다. AppKit을 기본 UI로 두며 SwiftUI는 향후 필요한 보조 화면에만 부분 적용한다.

## 결정과 결과

[프로그램 구조](../program-structure.md)에 따라 제품 디렉터리를 실제 생성했다. 조립은 app, 화면 연결은 workspace, 동작 판단은 기능별 Swift 코드가 맡는다. CEF 타입은 Objective-C++ bridge 안에 격리하고 Swift 어댑터가 기능 계약을 구현한다. NSView 타입은 화면 연결 경계에서만 사용한다. 일반 웹 프로필은 하나로 공유한다. 앱 저장소와 웹 프로필은 분리하며 CEF DB를 직접 편집하지 않는다.

CEF는 웹 엔진이며 앱 전체가 아니다. OS 기능은 macOS 경계로 연결한다. 현재 웹 알림 경로와 충돌하는 별도 UNUserNotificationCenter 조회·요청은 제품에 넣지 않는다. 이 선택 때문에 OS 알림 상태 자동 조회는 별도 지원 문제로 남으며 지원 여부를 숨기지 않는다.

기존 검증 코드는 기능 동작·엔진 처리 부분을 연결하되 mailbox·고정 슬롯·가상 사이트 등 실험 장치는 제외한다. 앱·bridge·helper 빌드 단위를 계획했고 이번에는 Xcode 프로젝트나 실행 코드를 만들지 않았다. 현재 의존성 제한은 폴더와 설계 규칙이며 컴파일 타깃 경계는 프로젝트 구성 때 반영한다. 원본 문서와 실험 코드는 보존했다. 추가 검증·앱 실행·새 의존성 설치는 수행하지 않았다.

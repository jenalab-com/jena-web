# CEF 영상·로그인 호환성 구현안

작성일: 2026-11-12
상태: 구현 방향 정리. 엔진 교체·대규모 다운로드·빌드·앱 실행은 하지 않았다.

## 1. 결론

**Swift·AppKit 제품 구조와 CEF는 유지한다. 영상은 코덱 지원 CEF 배포본으로 보완하고, 로그인은 원래 웹 인증 문맥을 보존하는 경로를 완성한다.** CEF가 처리할 수 없는 기능에는 앱 내부의 macOS 네이티브 기능 또는 내부 렌더링 경로를 보완한다. 사용자 결정에 따라 외부 브라우저로 넘기는 경로는 구현하지 않는다.

코덱 문제를 이유로 React/Electron으로 전환하거나 기존 탭·설정·기록·북마크를 다시 만들지 않는다. CEF를 채택할지 다시 판단하는 검증 차수도 열지 않는다. 외부 브라우저에서의 성공을 앱 내부 기능 완료로 간주하지 않는다.

우선순위는 ① 코덱 포함 엔진 공급 경로와 패키징 ② Pinterest 팝업·인증 문맥 ③ 남는 제약에 대한 앱 내부 보완 경로다. 두 문제를 한 번의 엔진 변경으로 모두 해결한다고 가정하지 않는다.

## 2. 사실과 가정

### 확인된 사실

- 현재 배포본: `156.0.27+ga10dae3+chromium-156.0.8078.88_macosarm64_minimal`.
- CEF commit: `a10dae3408911466b2d90409cc3355cbf6043ffb`.
- Chromium commit: `8954d18543712dc11b97c3aca0a6e714aa2d7dcd`.
- 제품 CMake는 외부 `CEF_ROOT`를 사용한다. Swift UI는 이미 엔진 연결부와 분리되어 있다.
- TikTok 재생 불가 보고 시 확인한 제품 로그에 `DEMUXER_ERROR_NO_SUPPORTED_STREAMS`가 23회 있었다. 읽은 로그의 최근 구간 기준이며 영상 URL/정확한 코덱은 확인하지 않았다.
- CEF 기본 구성은 proprietary codecs를 비활성화한다. H.264/AAC 지원은 빌드 구성과 관련된다. [CEF 유지관리자 설명](https://github.com/chromiumembedded/cef/issues/3559)
- 사용자는 Google 로그인이 페이지 이동 방식에서는 되는 것 같다고 보고했다. Pinterest는 중간 처리 뒤 팝업을 여는 것으로 관찰했다. 이는 사용자 관찰이며 앱이 내부 요청을 추적해 확정한 사실은 아니다.
- 제품에는 사이트별 팝업 허용과 CEF가 생성한 팝업을 앱 탭으로 수용하는 코드가 있다. Pinterest의 로그인 완료는 확인하지 않았다.

### 구현 가정과 범위

macOS arm64부터 진행한다. 비 DRM 일반 웹 영상과 일반 사이트 탐색이 우선이다. 정확한 MP4 코덱, 사이트별 차단 여부, 현재 CEF commit의 원격 소스 가용성과 요구 Xcode 버전은 추가 구현 입력으로 남아 있다. 현재 실패를 모두 H.264 하나로 단정하지 않는다.

`minimal`은 배포 패키지의 구성 구분이다. 이름이 `standard`인 기본 배포본으로 바꾸는 것만으로 코덱이 추가된다고 가정하지 않는다. “CEF는 영상 재생 불가”도, “코덱을 넣으면 모든 동영상 사이트 해결”도 올바른 결론이 아니다.

## 3. 영상: 코덱 포함 CEF를 주 경로로 사용

### 권장안: 버전을 고정한 커스텀 CEF 배포본

가능하면 현재 CEF/Chromium revision과 arm64를 유지하고, H.264 영상과 AAC 음성을 포함하도록 CEF 자체를 빌드한다. 최초 후보 GN 설정은 다음과 같다.

```text
proprietary_codecs=true
ffmpeg_branding="Chrome"
```

이는 **CEF/Chromium 소스 빌드 설정**이다. Jena의 CMake에 변수를 추가하거나 실행 인자를 붙여 이미 내려받은 framework에 코덱을 켜는 옵션이 아니다. 실제 GN 인자 전체는 해당 revision의 빌드 문서와 맞춰 작성한다. Google의 CEF 빌드 안내도 이 조합을 제시한다. [빌드 안내](https://support.google.com/webdesigner/answer/10043691?hl=en)

필요 산출물은 framework뿐 아니라 같은 버전의 headers·wrapper·resources를 포함한 일관된 CEF 배포 패키지다. Chrome에서 라이브러리를 뽑아 섞거나 인터넷에서 임의의 ffmpeg 파일을 받아 교체하는 방식은 사용하지 않는다.

제품 기능은 그대로 두고 `CEF_ROOT`와 패키징 입력만 바꾸는 것이 목표다. H.264 영상뿐 아니라 AAC 음성도 포함해야 하며 MP4 직접 로드와 MSE 기반 재생을 같은 것으로 간주하지 않는다. 자동재생 정책·네트워크·GPU·DRM 문제는 코덱 지원과 별개다.

### 공급 방식

| 방식 | 사용 조건 | 유지 부담 | 판단 |
|---|---|---|---|
| 직접 고정 버전 빌드 | 소스·빌드 머신 확보 | 소스 동기화, 보안 업데이트, 빌드 자동화 | 기준 경로 |
| 출처가 확인되는 코덱 포함 CEF 공급 | 정확한 버전·arm64·API·재배포 조건 충족 | 공급자 업데이트 의존 | 직접 빌드 부담이 크면 대안 |
| 기본 CEF 패키지 종류만 변경 | 코덱 활성화 근거 없음 | 문제 그대로일 수 있음 | 해결안으로 취급하지 않음 |
| 다른 제품의 바이너리/코덱만 복사 | ABI·리소스·배포 조건 불명 | 장애와 업데이트 부담 큼 | 사용하지 않음 |

직접 빌드는 앱 빌드보다 규모가 크다. CEF 자동 빌드 문서는 최소 16GB RAM과 200GB 여유 공간을 제시하지만, 이는 이 프로젝트의 현재 revision에 대한 실측 견적은 아니다. 실제 디스크·도구·작업 위치를 먼저 산정하고 대규모 다운로드를 시작한다. 빌드 소요 시간을 근거 없이 확약하지 않는다. [자동 빌드 환경](https://github.com/chromiumembedded/cef/blob/master/docs/automated_build_setup.md)

코덱을 포함한 배포에는 오픈소스 고지와 코덱 관련 배포 조건을 별도로 정리해야 한다. 로컬 동작과 제품 재배포 가능 여부는 다르며 무료 배포만으로 조건이 사라진다고 가정하지 않는다. 비용·계약 필요 여부는 배포 형태에 따라 확인해야 하며 이 문서가 법률 판단을 대신하지 않는다. [공식 안내의 코덱 항목](https://support.google.com/webdesigner/answer/10043691?hl=en)

### 현재 패키징에서 먼저 고칠 지점

`BuildSupport/package_app.py`는 앱 안에 framework가 이미 있으면 복사를 생략한다. 같은 빌드 폴더에서 `CEF_ROOT`만 바꾸면 **이전 framework가 남을 수 있다.**

엔진 연결 작업은 다음 순서로 한다.

1. 현재 앱·소스·사용자 프로필을 보존한다. 기존 실행 프로세스를 임의 종료하지 않는다.
2. 새 CEF 산출물은 기존 vendor와 별도 위치에 둔다. source revision, GN 인자, patch, 플랫폼, 체크섬을 기록한다.
3. `build/product-codecs` 같은 별도 CMake 디렉터리에서 headers·wrapper·framework를 함께 빌드/패키징한다. 기존 앱 산출물을 덮어쓰지 않는다.
4. 패키저에 입력 framework 식별값과 기존 bundle 식별값 비교를 추가한다. 불일치 시 조용히 기존 것을 사용하는 대신 빌드를 중단한다. 교체는 명시적인 별도 산출물에서 진행한다.
5. 실행 전 산출물 경로를 구분한다. 같은 앱 식별자·프로필의 구/신 버전을 동시에 실행하지 않는다. 기본 동작으로 사용자 로그인 데이터를 삭제·초기화하지 않는다.

새 framework로 H.264/AAC 지원을 제공하는 것과 TikTok 사이트 전체가 정상 동작하는 것은 별도 완료 항목이다. 이번 문서 작성에서는 실행 검사를 하지 않는다. 추후 사용자가 실제 사용하는 과정에서 발견한 오류를 해당 구현에 한정해 수정한다.

## 4. macOS 기능을 활용하는 대안

| 경로 | 가능한 용도 | 한계와 결정 |
|---|---|---|
| CEF 내부 macOS 하드웨어 디코딩 | 웹 페이지 안에서 재생하며 시스템 디코더 활용 | 코덱 노출과 빌드 구성도 필요. OS에 디코더가 있다는 이유만으로 현 CEF가 재생되지는 않음 |
| AVPlayer/AVKit | 앱이 소유하거나 정식 접근 가능한 직접 미디어 URL의 별도 플레이어 | TikTok의 JS·MSE·blob URL·인증·UI를 통째로 대신하지 못함. 일반 웹 영상의 첫 해결책으로 사용하지 않음 |
| WKWebView 보조 탭 | macOS WebKit으로 특정 페이지 전체를 별도 렌더링 | CEF와 쿠키·세션·탭 엔진 수명 관리가 갈라짐. Google 로그인 보장도 없음. 코덱 엔진 공급이 막힌 경우에만 별도 범위로 검토 |
| 외부 브라우저로 넘기기 | 사용자 결정으로 제외 | 구현 대상에 포함하지 않음 |

CEF의 OS 디코딩 전용 제안에는 H.264 하드웨어 경로와 AAC 등의 제약이 따로 논의되어 있다. 과거 제안만으로 현재 macOS에서 완성된 대체재라고 단정하지 않는다. 우선은 코덱을 포함한 일관된 CEF 배포본을 기준으로 한다. [관련 CEF 이슈](https://github.com/chromiumembedded/cef/issues/3559)

Widevine 등 DRM 보호 콘텐츠는 일반 H.264/AAC 지원과 별개다. 이번 TikTok 오류를 DRM 오류로 판정할 근거는 없다. 코덱을 포함하면 유료 스트리밍 서비스까지 지원된다고 약속하지 않는다.

## 5. Pinterest·Google 로그인: 세 가지 경계를 분리

### A. 팝업 생성 전 처리

중간 네트워크 요청·스크립트·브라우저 인증 API 처리 뒤 `window.open`이 호출될 수 있다. 클릭의 일시적 사용자 활성 상태가 사라지는 경우가 후보지만 실제 Pinterest 구현으로 확정하지 않는다. 팝업 callback까지 도착하지 않는다면 `OnBeforePopup`만 수정해서는 해결되지 않는다.

구현할 관찰 정보는 사건 종류, 탭 ID, 팝업 생성/차단/실패, 정규화한 origin 정도다. OAuth 전체 URL, code/state/token, 쿠키, 자격 증명은 기록하지 않는다. 네트워크 요청 내용을 무차별 수집하지 않는다.

### B. 팝업을 앱에 연결하는 처리

원래 엔진이 생성한 browser를 받아 `opener`, `postMessage`, POST, redirect, 동일 프로필을 보존한다. 이미 구현된 사이트별 팝업 허용은 유지한다. 생성 실패·차단을 침묵시키지 않는다.

빈 팝업을 먼저 열고 나중에 이동시키는 흐름, 이름 있는 창 재사용, 완료 후 닫힘을 지원 대상에 포함한다. `OnBeforePopup`과 `OnOpenURLFromTab`이 같은 흐름을 중복 처리하는지, 후자가 인증 요청을 URL만 복사한 GET으로 바꾸는지 코드 경계를 정리한다. Google 호스트만 보고 무조건 새 탭으로 재발행하지 않는다.

사용자가 관찰한 페이지 이동 방식은 그대로 보존한다. 사이트가 제공하지 않는 redirect 로그인 방식을 앱이 스크립트로 강제하거나 popup URL을 현재 페이지에 억지로 로드하지 않는다. 창 간 인증 메시지가 깨질 수 있다.

### C. 인증 제공자의 정책·지원 범위

Google은 개발자가 제어하는 embedded user-agent의 OAuth 요청을 제한한다. 페이지 이동이 일부 경우 동작한다는 사실만으로 모든 Google 로그인 경로의 지속 지원을 약속할 수 없다. 현재 Pinterest 장애가 정책 거절이라고 확정한 것도 아니다. [Google OAuth 정책](https://developers.google.com/identity/protocols/oauth2/policies)

CEF의 Chrome style이나 User-Agent 문자열 변경만으로 Google Chrome이 되거나 정책상 허용되는 것은 아니다. 제한을 숨기는 방식을 제품 해결책으로 삼지 않는다.

`ASWebAuthenticationSession`은 **Jena 자체의 OAuth client와 반환 경로를 설계할 수 있을 때** 유용하다. 임의의 Pinterest OAuth 흐름을 옮겨 띄운다고 그 결과가 CEF의 Pinterest 로그인 세션이 되지는 않는다. 외부 브라우저/인증 세션의 쿠키를 앱에 자동 이식하는 범용 API로 취급하지 않는다. [Apple 인증 세션](https://developer.apple.com/documentation/authenticationservices/aswebauthenticationsession)

제공자 제한으로 현재 내부 경로에서 로그인할 수 없다면 사이트가 제공하는 다른 내부 로그인 흐름과 앱 내부 엔진 보완 가능성을 구분해 다룬다. 외부 브라우저로 넘기지 않는다. 제공자 제한을 해소할 방법이 확인되지 않으면 앱 내부에서 미해결 상태로 명확히 설명하며, 해결됐다고 보고하지 않는다.

## 6. 구현 작업 순서와 완료 범위

| 순서 | 실제 작업 | 산출물/완료 상태 |
|---|---|---|
| 1 | CEF 코덱 배포 경로 준비 | 고정 revision·빌드 인자·공간/도구 요구·별도 산출물 위치. 공급 가능성 확인 전 다운로드 시작하지 않음 |
| 2 | 패키징의 엔진 식별·불일치 처리 | 오래된 framework가 섞이면 명확한 빌드 오류. 기존 앱 보존 |
| 3 | 코덱 포함 CEF 생성 또는 확보·연결 | headers/wrapper/framework 일치한 별도 Jena 앱. 실제 재생을 보지 않았다면 빌드 완료로만 보고 |
| 4 | 인증 팝업의 원래 문맥과 수명 연결 | 차단/생성 실패 안내, 창 생성·재사용·완료 닫힘 경로. 실제 인증 완료와 구분 |
| 5 | 앱 내부 보완 | 사이트가 제공하는 내부 로그인 방식 또는 필요한 내부 네이티브 기능 연결. 외부 브라우저 호출 제외 |

목표 동작은 웹 영상의 화면과 소리 재생, 로그인 후 원래 사이트에서 인증 상태 반영 및 사이트 유효기간 내 유지다. 빌드 성공만으로 이 목표 달성을 선언하지 않는다. 새 검증 차수나 기존 전체 기능 재검증을 계획하지 않으며, 자동 테스트·수동 검사·앱 실행은 이번 정리 범위에 포함하지 않는다.

## 7. 이번에 하지 않은 변경

기존 CEF 바이너리, 앱 실행 상태, 사용자 프로필, 시스템 권한, 소스 동작을 변경하지 않았다. 새 빌드 서버·유료 서비스·대규모 다운로드도 시작하지 않았다. 이 문서는 구현 경로를 구체화한 것으로, 새 엔진의 재생 성공이나 Pinterest 로그인 해결을 보고하는 문서가 아니다.
